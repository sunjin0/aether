# 计划文档格式规范（对齐 Codex / Claude 计划模式）

> 本规范定义 Deep Agent「计划先行 + 计划确认」中 **Markdown 计划文档（`document`）** 与配套结构化契约 `{complex, document, tasks}` 的精确格式。Deep Agent 按此生成计划，Admin 按此持久化与投递审批卡片，Dashboard 按此渲染。
>
> 状态：已随 [持续智能体会话记忆与动态执行实施跟踪](持续智能体会话记忆与动态执行实施跟踪.md) 的流程精化交付，配套代码 `80dce47`、`6e746f5`、`f491035`、`826e0d9`。

## 1. 定位与目标

计划文档是对一次 Deep Task 的「干什么、为什么、怎么干、怎么算完成」的**人类可读说明**。它面向最终用户展示，也被模型自身作为执行契约使用。设计对齐 Codex / Claude 计划模式的核心特征：

| 特征 | Codex / Claude | 本平台 |
| --- | --- | --- |
| 计划先行 | 先生成计划再动手 | 生成 `plan` 后暂停，进入审批 |
| 方案说明 | 计划文档包含方案与理由 | `document` 字段（Markdown） |
| 勾选清单 | `- [ ]` 逐步勾选 | 步骤 `tasks` 数组 + Dashboard 可勾选多选框 |
| 逐步骤验证 | 每步确认结果 | `step.verified` 回调 + `[STEP_VERIFIED]` 标记 |
| 动态调整 | 观察后可改计划 | 计划版本化 + 目标变更路由 |

**原则：**

1. `document` 是给人看的；`tasks` 是给机器和审计看的。两者必须一致：`document` 中「执行步骤」清单就是 `tasks` 的可读渲染，步骤数量、标题、顺序一一对应。
2. 计划是**执行契约**：批准后按序执行、逐步验证，不展示模型原始思维链。
3. 未获批准前**不执行**任何有副作用行动；简单任务由 `complex=false` 跳过审批门，但计划仍展示。

## 2. 端到端流程

```text
用户消息
  → resolveTaskRoute（会话有活跃任务即复用，不堆叠新任务）
      ├ 改为/重新 → GOAL_CHANGED（重规划）
      └ 其他回复   → CONTINUE（继续当前任务）
  → analyze_requirements（需求分析）
      └ 缺失关键信息 → ask_user 提问补充，再规划
  → 生成计划 {complex, document, tasks}
      ├ complex=false → 直接执行（单步计划仍展示）
      └ complex=true  → 暂停，发 plan.approval.required
          → Admin 生成 deep_plan_approval 卡片，任务 WAITING_APPROVAL
          → 用户批准 → /resume {plan_approved:true} → RUNNING
  → 按序执行步骤，每步验证 → step.verified 回调
  → 最终回复剥离 [STEP_VERIFIED] 标记 → run.completed
```

审批门使用**模型判定的复杂度**（`task_state.complex`），而非步骤数。模型按复杂度生成 1–6 步计划；只有复杂任务才要求计划确认。

## 3. Markdown 计划文档格式（`document`）

### 3.1 结构模板

`document` 是一段字符串，内容为 UTF-8 Markdown，供审批卡片与工作区直接渲染。**建议**结构如下：

```markdown
# <任务标题>

## 目标
一句话说明本次任务要达成什么、交付物是什么。

## 背景
现状、已确认信息、前置任务结论（如有）；无则省略本段。
说明为什么需要这个方案，避免什么风险。

## 方案
分点说明打算怎么做、为什么这样做、边界是什么。
（复杂任务必填；简单任务可省略或合并进步骤。）

## 执行步骤
- [ ] 1. <步骤标题>
- [ ] 2. <步骤标题>
- [ ] 3. <步骤标题>

## 风险与注意
- 列出已知风险、需要用户注意的事项、不能触碰的边界。

## 验收标准
- 可验证的完成标准（尽量可测量、可观察）。
```

### 3.2 写作约束

- **标题**：与任务标题一致（`#` 一级标题），不超过 40 字。
- **目标**：一段话，明确交付物。
- **执行步骤**：`- [ ] N. 标题` 的有序清单，**必须**与结构化 `tasks` 数组一一对应（同数量、同顺序、同标题）。每步标题 ≤ 40 字，动词开头，可独立验证。
- **禁止内容**：不写原始思维链、不写模型内部决策过程、不泄露 token / apiKey / 委派令牌 / 完整敏感工具输出。
- **语言**：跟随用户会话语言（中文会话用中文）。
- **脱敏**：正文不得包含密码、令牌、私钥或未脱敏文件内容。

### 3.3 完整示例（复杂任务）

```markdown
# 分析合同高风险条款并生成整改清单

## 目标
审查《采购合同》初稿，识别高风险条款，输出一份按风险等级排序的整改清单。

## 背景
用户已上传合同 PDF（共 12 页）。仅审查合同正文，不涉及附件中的报价单。

## 方案
分三段推进：先逐条抽取合同条款并归类；再按赔付、违约、知识产权、数据合规四个维度评估风险等级；最后按高→中→低汇总整改建议。

## 执行步骤
- [ ] 1. 抽取合同全部条款，按章节归类并编号
- [ ] 2. 逐条评估风险：赔付责任、违约金比例、知识产权归属、数据合规
- [ ] 3. 对高风险条款给出修改建议与理由
- [ ] 4. 生成按风险等级排序的整改清单（Markdown 表格）

## 风险与注意
- 违约金比例若超过行业惯例（>30%），需单独提示。
- 知识产权条款默认不删改原文，只给出建议。
- 不修改、不导出合同原文到外部。

## 验收标准
- 输出包含全部 12 页合同对应条款的风险映射；
- 高风险条款均有修改建议；整改清单可按风险等级排序。
```

对应的结构化 `tasks`（见第 4 节）应含 4 个步骤，标题与上表一致。

### 3.4 简单任务示例（不进入审批）

```markdown
# 查询当前时间
## 目标
返回服务器当前时间与日期。
## 执行步骤
- [ ] 1. 调用 get_current_time 获取当前时间
## 验收标准
- 返回可读的本地时间。
```

## 4. 结构化契约 `{complex, document, tasks}`

`plan.updated` 与 `plan.approval.required` 的事件 `data` 均携带该结构：

```json
{
  "complex": true,
  "document": "## ...（第 3 节 Markdown 文档）...",
  "tasks": [
    {
      "id": "1",
      "title": "抽取合同全部条款，按章节归类并编号",
      "status": "PENDING",
      "resultSummary": "",
      "idempotencyKey": "task-x:1",
      "attemptCount": 0,
      "startedAt": null,
      "completedAt": null
    }
  ]
}
```

### 4.1 字段定义

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `complex` | boolean | 是 | 模型直接判定任务是否复杂。审批门依据，非步骤数。 |
| `document` | string | 是 | Markdown 方案文档（第 3 节格式）。 |
| `tasks` | array | 是 | 步骤数组，1–6 个，与 `document` 步骤清单一一对应。 |
| `tasks[].id` | string | 是 | 步骤稳定标识（建议 `"1"`、`"2"`…）。Admin 用它生成 `stepKey` 与幂等键。 |
| `tasks[].title` | string | 是 | 步骤标题，与 `document` 勾选项一致。 |
| `tasks[].status` | string | 否 | `PENDING` / `RUNNING` / `COMPLETED` / `FAILED`；缺省由 Admin 按前版本推导。 |
| `tasks[].resultSummary` | string | 否 | 步骤验证摘要（`step.verified` 回填）。 |
| `tasks[].idempotencyKey` | string | 否 | 稳定幂等键；缺省 Admin 生成 `taskId:stepKey`，用于恢复时跳过已完成副作用。 |
| `tasks[].attemptCount` | integer | 否 | 尝试次数。 |
| `tasks[].startedAt` | long | 否 | 开始时间戳（ms）。 |
| `tasks[].completedAt` | long | 否 | 完成时间戳（ms）。 |

> **注意**：`tasks[].idempotencyKey` 在首次规划可省略；Admin 的 `AgentRunPlanServiceImpl.recordPlan` 会以 `defaultIfBlank(taskId, runId) + ":" + stepKey` 兜底。恢复执行时，已完成步骤的副作用动作绝不重复。

### 4.2 事件载体

| 事件 | data 内容 | 触发时机 |
| --- | --- | --- |
| `plan.updated` | `{reason, summary, complex, document, tasks}` | 每次生成 / 重规划；Admin 投影为计划版本 |
| `plan.approval.required` | `{plan, document}` | 仅复杂任务，暂停等待批准 |

`reason` 取值：`INITIAL`、`TOOL_RESULT`、`USER_INPUT`、`GOAL_CHANGED`、`STEP_FAILED`、`RESUME`、`COMPLETED`；未知值 Admin 归一化为 `OBSERVATION`。

## 5. 审批门与交互卡片

### 5.1 审批门

- Deep Agent 生成计划后，按 `task_state.complex` 决策：
  - `complex=false`（简单任务）：不暂停，直接执行；仍发 `plan.updated`（单步计划 + 答案在 Dashboard 展示）。
  - `complex=true`（复杂任务）：暂停，发 `plan.approval.required`。
- 运行请求固定携带 `plan_approval_required=true`（`DeepAgentRunService`）。

### 5.2 `deep_plan_approval` 卡片 questionConfig

Admin 的 `createPlanApproval` 将事件转换成交互消息 `questionConfig`：

```json
{
  "type": "group",
  "layout": "confirm",
  "question": "请确认执行计划，批准后将按计划执行。",
  "approvalType": "deep_plan_approval",
  "runId": "run-xxxx",
  "document": "## ...（Markdown 方案文档）...",
  "plan": [
    { "id": "1", "title": "抽取合同全部条款，按章节归类并编号", "status": "PENDING" }
  ]
}
```

交互消息 `messageType=interaction`、`interactionType=group`、`interactionStatus=pending`；任务进入 `WAITING_APPROVAL`（原因「等待计划确认」）。

### 5.3 批准与拒绝语义

- **批准**：`POST /api/agent/session/task/{taskId}/input`（或既有 `resumeToolApproval`）携带答案，Admin 将交互消息置 `answered`，并向 Deep Agent 发送 `POST /v1/runs/{runId}/resume`，body：

  ```json
  {
    "run_id": "run-xxxx",
    "plan_approved": true,
    "answers": { "selected_steps": [1, 2, 3] }
  }
  ```

  `answers` 为用户原始答案整体转发（与 `deep_ask_user` 同约定），步骤多选框所选步骤由 Deep 服务解释；未勾选步骤不执行（可选实现）。成功后任务 `RUNNING`。
- **拒绝 / 取消**：可走目标变更（聊天「改为/重新」）触发 `GOAL_CHANGED` 重规划，而非硬删除。

## 6. 步骤状态机与验证

### 6.1 步骤状态

```text
PENDING → RUNNING → COMPLETED
                ├ → FAILED
                └ → SUPERSEDED（新版本发布时未完成步骤自动失效）
```

- 已完成步骤不可改写；重规划后不再适用的未执行步骤置 `SUPERSEDED`，恢复时不重放过时副作用。
- Deep Agent 每步开始时发 `step.started`（data 含 1-based `stepIndex`），Admin 的 `markStepRunning` 将步骤置 `RUNNING` 并记 `startedAt`；已完成/失败/失效步骤不改写。
- 计划记录在 `agent_run_plan` / `agent_run_plan_version` / `agent_run_plan_step`（`task_id` 维度延续，`run_id` 兼容旧接口）。

### 6.2 `step.verified` 验证协议

- 执行器按计划顺序执行；每完成一步，在流中输出 `[STEP_VERIFIED]` 标记，并向 Admin 回调：

  ```json
  {
    "event_type": "step.verified",
    "data": { "stepIndex": 3, "verification": "已生成整改清单，覆盖全部 12 页条款，5 项高风险" }
  }
  ```

- Admin 的 `markStepVerified` 将 `verification` 写入对应步骤的 `resultSummary` 并置 `COMPLETED`。
- **缺省回退**：若某步未携带标记，Deep Agent executor 以工具结果摘要生成缺省验证摘要，再经 `step.verified` 下发；Admin 端不合成验证摘要。
- **最终回复**：完成后的最终回答必须剥离 `[STEP_VERIFIED]` 标记（`_strip_step_verified`），不得泄漏给用户。

### 6.3 计划版本化

每次重规划发布新版本，记录 `reason` 与 `summary`（≤500 字）：

| reason | 触发 |
| --- | --- |
| `INITIAL` | 首次规划 |
| `TOOL_RESULT` | 工具结果导致路径调整 |
| `USER_INPUT` | 用户补充信息后重规划 |
| `GOAL_CHANGED` | 用户「改为/重新」变更目标 |
| `STEP_FAILED` | 步骤失败后调整 |
| `RESUME` | 中断/重启后恢复 |
| `COMPLETED` | 计划完成 |

Dashboard **只展示最新版本**，标注版本原因；旧版本保留可审计。

## 7. 需求分析与动态调整

### 7.1 需求分析先行

规划**之前**执行 `analyze_requirements`：检查任务缺失的关键信息（如分析任务缺少源文件、目标任务缺少对象）。缺失则先 `ask_user` 提问补充，**不盲目生成规划**；补充完成后才开始规划。真实验证：任务「请分析合同风险」（无合同）→ 提问补充 → 规划 → 复杂审批 → 执行 → 完成。

### 7.2 每 Session 一个任务

`resolveTaskRoute` 决策：会话有活跃任务即复用，不堆叠新任务：

| 用户输入 | 路由 | 结果 |
| --- | --- | --- |
| 「改为…」「重新…」 | `GOAL_CHANGED` | 同 Task 重规划，发布新计划版本 |
| 其他回复 | `CONTINUE` | 同 Task 继续执行 |

### 7.3 中断与继续（聊天化）

- **中断** = 聊天输入「停止」；不再使用工作区「暂停/继续」按钮。
- **继续** = 回复新消息；服务重启后从最后安全 checkpoint 恢复，已完成副作用动作不重复。

## 8. 落地实现指引

### 8.1 Deep Agent（生成端）

1. `analyze_requirements` → 缺失信息先 `ask_user`。
2. 生成 `{complex, document, tasks}`；`document` 严格按第 3 节格式，`tasks` 与步骤清单一一对应。
3. `complex=true` → 发 `plan.approval.required` 并暂停；`complex=false` → 直接执行。
4. 执行中按序验证，每步发 `step.verified`；最终回复剥离 `[STEP_VERIFIED]`。

### 8.2 Admin（持久化端）

1. `plan.updated` → `recordPlan` 投影新版本 + 步骤（`tasks` 解析，缺省幂等键兜底，旧版本未完成步骤置 `SUPERSEDED`）；快照保留完整 `{complex, document, tasks}`。
2. 计划详情 API（`GET /api/agent/session/task/{taskId}`、`GET /api/agent/run/{id}/plan`）返回 `AgentRunPlanVo`，各版本含 `complex` / `document`，供 Dashboard 刷新后恢复方案文档。
3. `plan.approval.required` → `createPlanApproval` 生成 `deep_plan_approval` 卡片（含 `document` + `plan`）。
4. 批准 → `resumeToolApproval` 投递 `{plan_approved:true, answers}`（answers 为所选步骤等原始答案），恢复执行。
5. `step.started` → `markStepRunning` 置 `RUNNING` + `startedAt`。
6. `step.verified` → `markStepVerified` 写 `resultSummary` + `COMPLETED`。

### 8.3 Dashboard（渲染端）

1. 展示最新计划版本的 `document`（方案文档）与步骤勾选清单。
2. 步骤状态国际化（PENDING/RUNNING/COMPLETED/FAILED/SUPERSEDED）。
3. 计划确认卡片展示方案文档 + 多选框；批准随答案传递所选步骤。
4. 不展示「运行概览」、不展示思维链。

## 9. 验收要点

1. 复杂任务：`complex=true` → 生成 3–5+ 步计划 + 方案文档 → `WAITING_APPROVAL` → 批准 → 按序执行 → 全部步骤 `COMPLETED`。
2. 简单任务：`complex=false` → 单步计划直接执行 `COMPLETED`，无审批暂停。
3. `document` 与 `tasks` 步骤数、标题、顺序完全一致。
4. 需求缺失时先提问，补充前 `plan.updated=0`。
5. 中断/重启后继续，已完成副作用动作不重复，计划版本出现 `RESUME`。
6. 最终回复 `[STEP_VERIFIED]` 出现 0 次。
