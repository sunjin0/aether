# Aether 企业 Agent 平台多期开发路线图

> 状态：实施基线（代码交付持续进行，生产验收分阶段推进）。以现有 Java Control Plane、Deep Agent Runtime、MCP、Workflow、Knowledge 和 Sandbox 能力为基础；已完成项以测试和构建证据为准，外部系统联调项以演练记录为准。

## 1. 总体目标

将 Aether 演进为可构建、运行、治理和交付企业 Agent 应用的平台。核心原则是：LLM 负责理解与规划，平台负责权限、执行、状态、审计和策略。

## 2. 分期总览

| 期次 | 主题 | 目标 | 建议周期 |
| --- | --- | --- | --- |
| 第 0 期 | 基线与契约 | 统一术语、数据边界、质量门禁 | 1 周 |
| 第 1 期 | Execution 与可观测性 | 建立统一运行账本、Trace、指标和成本口径 | 2–3 周 |
| 第 2 期 | 评测与发布质量 | 将知识、Agent、Workflow 评测纳入发布流程 | 2–3 周 |
| 第 3 期 | 企业治理 | Agent Identity、策略、数据范围和 Secrets | 3–4 周 |

建议按 18–25 周规划；各期可并行开展前端设计和测试用例准备，但后续期的生产发布依赖前一期验收通过。

## 3. 第 0 期：基线与契约

### 范围

- 定义统一 Execution 模型：`executionId`、`parentExecutionId`、`traceId`、actor、resource、status、时间、Token、cost、error。
- 定义状态码、Trace 传播和脱敏规则；统一 Agent Run、Workflow Instance、Tool Call、Sandbox Task 的关联方式。
- 建立 API 契约测试、Flyway 迁移检查、关键链路集成测试的 CI 门禁。
- 梳理现有文档的事实来源，明确各模块负责人及变更流程。

### 验收

- Execution 数据字典和状态机评审通过。
- Agent、Workflow、Tool、Sandbox 的关联字段和兼容策略确定。
- CI 能执行编译、迁移校验及核心模块测试。

## 4. 第 1 期：统一 Execution 与可观测性

### 交付物

- 持久化 Execution 账本及父子树，兼容既有 `agent_run`、工作流实例、工具日志和 Sandbox 任务。
- Trace 查询页/API：能从 Workflow 定位其 Agent、RAG、Tool、子 Agent、通知等子执行。
- 运行指标：调用量、成功率、P50/P95 延迟、等待时长、工具失败率、队列积压。
- 用量与成本：模型 Token、Embedding、Rerank、工具和 Sandbox 时长；成本先采用可配置估算单价。
- 审计脱敏：请求、响应和异常按敏感级别保留摘要或引用，不写入 Secrets。

### 验收

- 一次工作流调用 Agent 和 Tool 后，可在单一 Trace 中完整查看树、状态和耗时。
- 运行失败可定位至具体子执行和错误码。
- 面板数据可按应用、Agent、Workflow、模型、用户和时间筛选。

## 5. 第 2 期：评测与发布质量

### 交付物

- 复用现有知识检索评测，补充 Agent 任务评测、工具选择/安全评测和 Workflow 回归评测。
- 构建 Evaluation Center：评测集、版本快照、运行、基线、差异比较和报告。
- 发布门禁：Agent/Skill/Workflow 版本需通过指定评测阈值方可发布或需人工豁免。
- 引入测试数据脱敏、固定模型参数和可复现执行快照。

### 验收

- 能对一个版本运行评测、与基线比较并记录结果。
- 回归导致 Recall、成功率或安全指标低于阈值时阻止发布。
- 可追溯每条评测使用的版本、数据集、模型和执行 Trace。

## 6. 第 3 期：企业治理

### 交付物

- Agent Identity：Agent、Skill、Workflow 和 Tool 都以独立主体参与授权。
- 策略判定模型：`Subject + Resource + Action + Context -> Decision`，先实现平台内置策略，保留 OPA/Cedar/Casbin 适配边界。
- 数据范围（Data Scope）：知识库、连接器、业务对象支持应用/部门/区域等上下文约束。
- Secret Provider：本地加密实现与 Vault/Kubernetes Secret 等外部适配接口；运行时只传 `credentialRef`。
- Audit Center：统一检索授权拒绝、审批、Secret 使用和高风险工具操作。

### 验收

- 有效权限为 User、Agent、Skill、Workflow 和 Tool Policy 的交集，Skill 不可扩权。
- 未授权数据和高风险 Tool 调用在平台层被拒绝并留存审计。
- 任何 API、日志、Trace 和 Agent 上下文都不会返回 Secret 明文。

## 7. 第 4 期：扩展能力

### 交付物

- Connector 框架：安装、认证、健康检查、权限范围、版本和解绑生命周期；优先 Git、Jira、Confluence、数据库、Prometheus/Grafana。
- Skill 正式产品化：版本、资源、安装、上下文预算、运行快照与受控执行。
- Artifact 闭环：Agent/Sandbox 生成的报告、表格、PDF 等纳入版本、权限、存储、预览和 Trace。
- 插件/连接器发布规范和安全审核清单。

### 验收

- 管理员可用 UI 完成连接器配置、授权、绑定、健康检查和撤销。
- 一次 Skill 执行可生成受权限保护的 Artifact，并从运行 Trace 访问。
- 连接器或 Skill 被禁用后，后续执行立即失效且不影响已完成审计。

## 8. 第 5 期：应用与解决方案

### 交付物

- Application 模型：一个业务应用聚合 Agents、Skills、Knowledge、Workflows、Connectors、权限和配额。
- Solution 模型：可安装模板包，带版本、依赖检查、配置向导、升级和回滚。
- 首个官方 Solution：AI SRE，包含告警 Webhook、诊断 Workflow、知识库、Prometheus/Grafana/Kubernetes 连接器与人工审批修复。
- 面向终端用户的 Chat、Tasks、Files、History、Apps 入口与面向管理员的 Build/Connect/Observe/Admin 分区。

### 验收

- 可一键安装测试环境的 AI SRE Solution，并完成告警到人工审批的演示闭环。
- Solution 卸载或升级不会删除审计与历史 Artifact。
- 普通用户无需理解 MCP、RAG、Skill 等内部概念即可完成任务。

## 9. 第 6 期：企业规模化

### 交付物

- 多租户：tenant/workspace/project 分层隔离，数据、向量、对象存储、配额与审计全链路带 `tenantId`。
- 企业身份：OIDC/SAML、SCIM、组织同步和细粒度 RBAC/ABAC。
- 运行可靠性：Worker 横向扩容、任务恢复、限流、熔断、灾备演练和容量基线。
- OpenTelemetry：Trace、Metric、Log 对接企业观测平台。
- 运营治理：预算、配额、告警、保留策略、数据导出和合规报表。

### 验收

- 跨租户数据访问、向量检索、Artifact 下载和 Trace 查询均被隔离测试覆盖。
- 单个 Runtime/Worker 故障不丢失已持久化执行任务。
- 可将关键 Trace 和指标导出到标准 OTel 后端。

### Connector 凭据委派实施契约

为支持 Prometheus/Grafana/Kubernetes 等具体适配器，Connector 凭据必须沿用现有短期委派模型：Admin 在运行时按 `runId`、`userId`、`tenantId`、`connectorId` 和 `allowedTools` 生成短期 AES-GCM 凭据令牌；Java MCP Transport 仅通过内部 `X-Aether-Connector-Credential` 请求头转发，不将明文凭据放入工具参数、Prompt、审计或数据库；MCP Server 仅在请求作用域解密令牌，校验过期时间、租户、Connector 标识和工具范围后注入适配器；请求结束立即清理上下文，目标连接器只接收必要的 endpoint/token 字段。令牌 TTL 默认不超过 5 分钟，撤销和失败均不得回退到静态环境凭据。该契约完成后，按 Prometheus → Grafana → Kubernetes 顺序实现工具与健康检查适配，并为每个适配器提供越权、过期、租户不匹配和敏感信息不落盘测试。

### 当前状态勘误（2026-09-01）

文档前文的历史记录以本节为准：SCIM Users/Groups 已不再是只读接口；Prometheus、Grafana、Kubernetes 的只读 MCP 适配器及 Java 凭据委派链路已完成并通过专项/全量测试；OIDC/SCIM 已有可用实现，SAML 已接入 relying-party、租户绑定 RelayState 和 NameID 显式映射基础。Admin 已提供 OTLP metrics、默认关闭的标准 OTLP Trace/Logs，MCP 已提供默认关闭的标准 OTLP Trace/Log exporter。Admin OTel 已完成代码级验证，并已在本地 Collector 验收栈完成端点联调；本地 Keycloak 已验证 OIDC discovery 与 SAML metadata，本地 Docker Desktop Kubernetes 已验证 Connector 测试 Pod。完整生产 IdP/Collector 集成仍待企业环境验收。最新迁移门禁为 174 个迁移、最高版本 V176。

## 10. 贯穿每期的工程要求

- 数据库仅新增 Flyway 迁移，不修改已发布迁移。
- 每个新接口定义鉴权、幂等、审计、限流、错误码和脱敏行为。
- 每期至少提供单元、集成、契约和关键 E2E 测试；涉及 Agent 的变更额外提供评测集。
- 所有运行版本、策略和能力范围必须冻结到执行快照，保证事后可复现和可审计。
- 第 1 期开始在真实试点前执行安全评审和压测；第 5 期 AI SRE 试点作为产品验收样板。

## 11. 当前启动顺序

当前基础期至第 6 期骨架已完成；本地 OTel、Keycloak OIDC/SAML 和 Docker Desktop Kubernetes 联调已完成。下一步按剩余验收优先级推进：进行 AI SRE 真实基础设施试点、Connector/Skill 深度集成以及企业 Collector/IdP 生产联调；所有生产验收需保留外部 Collector、IdP 和基础设施环境证据。
