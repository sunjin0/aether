# Aether 生产变更与事故响应运行手册

**运行所有者：SRE｜适用环境：生产、灾备与共享基础设施**

## 文档控制

| 字段 | 内容 |
| --- | --- |
| 批准角色 | SRE 负责人、工程负责人、信息安全负责人 |
| 生效日期 | 2026-08-01 |
| 适用范围 | 生产、灾备、共享基础设施和客户可见服务 |
| 复审触发 | P1 事故、重大架构变更或季度运行复核 |

## 运行目标与职责

本运行手册定义生产变更与事故响应的最低控制要求。变更负责人对实施和回滚负责；事故指挥官对处置节奏与恢复判断负责；通信负责人对状态页和客户信息一致性负责；记录员保留时间线、决定和行动项。任何人发现风险都可停止变更并升级。

## 1. 变更分类

### 1.1 分类与提前期

标准变更为预先批准、低风险且有固定回滚步骤的操作，例如证书轮换和无模式配置更新。普通变更至少提前 2 个工作日提出，需包含测试证据、影响分析、监控指标、实施窗口和回滚负责人。高风险变更涉及数据库迁移、权限模型、向量索引格式、认证链路或跨区域流量切换，至少提前 5 个工作日评审。

### 1.2 冻结期与紧急例外

变更冻结期为每月最后 3 个自然日和年度财务结算窗口。P1 修复可在冻结期实施，但必须由值班 SRE 负责人及业务负责人双重批准，并在下一个工作日提交补充复盘。

## 2. 事故处置

### 2.1 分级、指挥与更新时间

P1：全量核心业务不可用或存在确认的数据泄露风险。15 分钟内建立指挥频道、指定事故指挥官和通信负责人；30 分钟内更新状态页。P2：关键功能降级但有可行绕行方案，4 小时内启动复盘。P3：一般缺陷进入常规迭代，不占用事故指挥流程。

### 2.2 恢复决策权

任何人在事故期间都可以提交证据，但只有事故指挥官可以宣布恢复。恢复条件包括：核心指标连续 30 分钟稳定、错误率回到基线阈值、队列积压趋势下降且回滚风险可接受。宣布恢复后仍需监控至少 60 分钟。

## 3. 复盘与预防

P1 复盘在恢复后 5 个工作日内完成，P2 在 10 个工作日内完成。复盘必须区分触发原因、放大因素、检测缺口和纠正行动；行动项应含负责人、截止日期和验证标准。禁止将“人为失误”作为唯一根因，也禁止在未验证前标记行动项完成。

## 4. 实施前检查清单

变更负责人须在窗口开始前确认：关联变更单已获批准、监控仪表板可用、值班人员与回滚负责人在线、数据库备份或快照已验证、客户通知已发送、实施脚本与回滚脚本经过同行评审。若任一前置条件不满足，应延期而不是在窗口内临时补救。

涉及知识库检索的变更还需验证索引兼容性、Chunk 重新生成成本、现有 Agent 的召回回归基线和异步任务队列容量。更新向量模型或嵌入维度时，必须准备双索引或完整重建方案；不能只更新配置后假设历史向量会自动兼容。

## 5. 运行期间的沟通纪律

事故频道采用统一格式：`时间 - 观察到的事实 - 正在采取的行动 - 下一次更新时间`。推测与已证实事实必须区分；例如“怀疑缓存命中率下降”不能表述为“缓存故障已确认”。通信负责人负责状态页、客户支持和内部管理层的一致信息，技术负责人不应同时承担所有沟通职责。

当客户报告影响但监控尚未告警时，应创建观察项并记录租户、区域、功能、请求 ID 和开始时间。不要因无法立即复现而关闭工单。连续 15 分钟无新信号时，可降低更新频率，但 P1 状态页仍应按 30 分钟节奏更新。

## 6. 恢复后的验证

宣布恢复不等于关闭事故。恢复后须确认 API 成功率、登录成功率、队列年龄、错误预算消耗、关键客户合成探针和后台任务吞吐均恢复到预期范围。若仅通过回滚恢复，应评估回滚是否遗留数据格式、索引版本或权限配置差异。

对造成数据写入失败的事故，需要执行补偿任务并抽样核验。对消息、Webhook 或索引任务，需要确认没有重复投递、重复计费或丢失任务。客户可见的恢复说明应明确“服务已恢复”“数据补偿进行中”或“仍有受限功能”，避免笼统使用“已解决”。

## 7. 值班交接

每次交接至少包含当前事件、已知风险、待验证假设、计划变更、关键仪表板、客户承诺和下一更新时间。接班人必须明确确认接收；仅在群组中发送文字不代表完成交接。若事故跨越两个值班班次，原事故指挥官应在交接后继续可联系 30 分钟，直到接班人熟悉上下文。
